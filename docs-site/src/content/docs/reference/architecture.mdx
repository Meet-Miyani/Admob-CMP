## How is AdMob CMP structured?

<ModuleMap />

| Module / Artifact | Purpose & Contents |
|---|---|
| `dev.avinya.ads:admob-cmp` | Umbrella artifact aggregating `admob-cmp-core` and `admob-cmp-compose` for Compose Multiplatform projects. |
| `dev.avinya.ads:admob-cmp-core` | Core engine: `AdManager`, full-screen controllers, native ad pool, consent state machine, diagnostics, and event streams. |
| `dev.avinya.ads:admob-cmp-compose` | Compose Multiplatform UI integration: `BannerAdView`, `NativeAdView`, and `rememberAdManager`. |
| `dev.avinya.ads.admob-cmp` (Gradle Plugin) | Gradle plugin managing version-stamped iOS native test framework dependencies and linker flags for Kotlin/Native test binaries. |

`androidMain` provides `AndroidGoogleAdManager` with slots, native pool, and banner handling over the Android GMA Next-Gen SDK, the `AdMob.manager(context)` singleton, and process lifecycle monitoring (`ProcessLifecycleOwner`).

`iosMain` provides `IosGoogleAdManager` over Kotlin/Native cinterop bindings, a Kotlin UIKit native-ad renderer, and application lifecycle event observers via `NSNotificationCenter`.

Separating `admob-cmp-core` from `admob-cmp-compose` allows projects using non-Compose UI architectures or custom UI wrappers to depend on `admob-cmp-core` directly without pulling in Compose Multiplatform dependencies.

## What lives in common code, and what is platform-specific?

The architecture follows a key principle: **one shared state machine, two thin platform adapters.** Every full-screen slot extends `FullScreenSlotCore`, which owns the load mutex, TTL-based FIFO caching (bounded by `AdCachePolicy.maxSize`), retry policies, consent gating, event emission, and `reloadAfterShow`. Platform classes implement only `loadAd`, `presentAd`, `destroyAd`, and `canPresent`.

Why this matters for applications: interstitial, rewarded, rewarded interstitial, and app-open formats share identical caching, state management, and retry behaviour across Android and iOS. A cache fix or state enhancement in common code takes effect across all full-screen ad formats simultaneously.

Format-specific handling remains encapsulated within platform adapters. A platform's `loadAd` method configures placement identifiers and targeting parameters appropriate for its format, whilst shared common code manages overall lifecycle, status transitions, and ad presentation ownership.

## Why does iOS ship bindings instead of binaries?

The iOS implementation compiles against official GMA and UMP XCFrameworks via Kotlin/Native **cinterop**. The `dev.avinya.ads.admob-cmp` Gradle plugin downloads header zips into `build/admob-cmp-ios-frameworks/` (a version-stamped build cache) strictly for header binding generation. The published library klibs contain header **bindings**, never Google's binary frameworks. The consuming iOS app links GMA and UMP natively using Swift Package Manager.

This approach was selected over alternative binary distribution models:
- **CocoaPods packaging:** Rejected to maintain primary alignment with Swift Package Manager across iOS projects.
- **Embedding static binaries (`staticLibraries` in `.def`):** Rejected because embedding binary frameworks breaks third-party mediation adapters due to duplicate Objective-C class symbols, pins the GMA version for every consumer, and introduces binary redistribution complexity.

As a trade-off, consuming iOS projects add the `GoogleMobileAds` and `UserMessagingPlatform` Swift packages directly in Xcode, ensuring the SPM major version matches the bound header version (`13.x` for GMA, `3.x` for UMP).

## How does the full-screen state machine work?

The ad cache carries a generation counter incremented by `clear()`. A load or scheduled reload operation started before a `clear()` call checks its target generation before storing results, preventing stale loads from populating a newly invalidated cache.

Ad presentation ownership is managed via a one-shot handle. The core state machine holds ownership until the platform slot hands execution off to the native SDK immediately before invocation. From that point onward, only the native SDK's completion callbacks (or a pre-hand-off cancellation) close the state.

This model guarantees two key public API behaviours:
1. `show()` is non-reentrant per controller: calling `show()` whilst a presentation is active returns `AdShowResult.NotReady` rather than queueing additional requests.
2. Coroutine cancellation after hand-off does not corrupt process-wide presentation signals, ensuring coordinators such as `AppOpenAdCoordinator` accurately reflect when an ad is active on screen.

## What is the threading model?

Native GMA and UMP SDK invocations are executed on `Dispatchers.Main.immediate` internally, ensuring all public APIs are main-safe and callable from any coroutine context. Component registries are lock-protected for thread safety. On iOS, delegate instances are strongly retained for the lifetime of their native owner to prevent premature Objective-C deallocation before terminal callbacks fire.

Using `Main.immediate` ensures synchronous execution when invoked from the main thread (avoiding unnecessary message queue posting) whilst correctly dispatching to the main thread when called from background threads. This ensures responsive state queries for Compose state bindings like `StateFlow.collectAsState`.

Coroutine cancellation is supported across all suspend APIs. Cancelling a `load()` operation aborts the network request and result storage. Cancelling a `show()` coroutine releases caller suspension; however, once hand-off to the native SDK has occurred, the native presentation completes naturally to prevent corrupted UI states.

## How do events flow?

```
platform SDK callback → slot / pool / controller
    → controller.events   (per-placement SharedFlow)
    → AdManager.events    (global SharedFlow)
```

The sealed `AdEvent` hierarchy includes `Loaded`, `LoadFailed`, `ShowFailed`, `Impression`, `Clicked`, `OpenedFullScreen`, `ClosedFullScreen`, `RewardEarned`, `Paid`, and iOS video events. Refer to [Revenue and paid events](/advanced/revenue-events/) for event payload structures and telemetry patterns.

Event streams use `SharedFlow<AdEvent>` so multiple collectors (such as UI components, analytics engines, and test harnesses) can observe events concurrently without triggering duplicate underlying SDK callbacks.

## What were the key design decisions?

| Decision | Rationale |
|---|---|
| Suspend functions and `Flow` instead of listener callbacks | Modern Kotlin coroutine approach. `show()` suspends until ad dismissal. |
| Placement-keyed, long-lived controllers | Centralised caching, retry, and lifecycle management. |
| Consent integrated into initialisation | Guarantees compliance before ad requests are attempted. |
| Bindings-only iOS distribution | Ensures mediation compatibility and SPM version flexibility. |
| Shared core caching | Delivers consistent caching behaviour across platforms independent of platform preloading APIs. |
| No bundled mediation adapters | Allows publishers to select and maintain platform-specific mediation dependencies. |
| `explicitApi()` and committed ABI dumps | Guarantees public API contract integrity via `checkKotlinAbi`. |

The library's public ABI definition is committed at `admob-cmp-core/api/admob-cmp-core.klib.api` (and the corresponding file for `admob-cmp-compose`), and verified during build checks.
