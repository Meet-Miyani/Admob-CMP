## What is App Tracking Transparency on iOS?

Since iOS 14.5, Apple requires applications to obtain user permission via the App Tracking Transparency (ATT) framework before accessing the device Advertising Identifier (IDFA). AdMob uses the IDFA to support ad personalisation and attribution reporting on iOS.

The AdMob CMP library provides access to ATT status and prompt requests via `adManager.tracking`, leaving prompt timing to the application lifecycle.

On Android, ATT does not apply: `adManager.tracking` is a no-op that always returns `AdTrackingAuthorization.NotApplicable`.

## Info.plist requirement vs runtime prompt call

Integrating ATT on iOS requires two distinct items:

1. **Info.plist usage description**: Add the `NSUserTrackingUsageDescription` key to your iOS application target's `Info.plist`. This string explains to the user why tracking permission is being requested. Adding this key declares your application's intent to iOS but **does not trigger the prompt by itself**.
2. **Runtime authorisation request**: Call `adManager.tracking.requestAuthorization()` at runtime to display the iOS system prompt.

```xml
<key>NSUserTrackingUsageDescription</key>
<string>This identifier is used to deliver personalised ads to you.</string>
```

If `NSUserTrackingUsageDescription` is omitted from `Info.plist`, iOS will not present the system dialog when `requestAuthorization()` is called, and IDFA access will remain unavailable. App Store review will also reject iOS builds missing this usage description when tracking APIs are referenced.

## What is the correct initialisation order?

The recommended production sequence on iOS is:

```kotlin
adManager.consent.gatherConsent(config)
adManager.tracking.requestAuthorization()
adManager.initialize(config, ConsentMode.InitializeOnlyIfAlreadyAllowed)
```

<InitSequence />

This sequence ensures:
- UMP consent is gathered first to establish whether ad requests are permitted under regional privacy regulations (such as GDPR).
- ATT authorisation is requested before starting Mobile Ads initialisation so the IDFA is available when initialisation and initial ad requests occur.
- Mobile Ads initialises via `ConsentMode.InitializeOnlyIfAlreadyAllowed` to avoid re-triggering UMP forms that were already handled.

<Aside type="caution">
Ad requests issued before ATT authorisation completes will be sent without an IDFA. These requests cannot retroactively attach an IDFA once authorisation is granted later. However, subsequent ad requests made after ATT approval will include the IDFA subject to platform SDK behavior and user system settings.
</Aside>

User tracking decisions are not locked permanently for the lifetime of the installation. A user who originally denied ATT permission can enable tracking later in iOS system settings (`Settings > Privacy & Security > Tracking`). Subsequent ad requests will reflect updated identifier availability.

## Requesting ATT from an initialisation hook

For applications using `gatherConsentAndInitialize`, use `AdInitializationHook` to sequence ATT cleanly inside the pre-initialisation phase:

```kotlin
AdConfig(
    appIds = AdAppIds(
        android = "ca-app-pub-…",
        ios = "ca-app-pub-…",
    ),
    initializationHooks = listOf(
        object : AdInitializationHook {
            override suspend fun onPhase(phase: AdInitializationPhase, config: AdConfig) {
                if (phase == AdInitializationPhase.BeforeMobileAdsInitialize) {
                    adManager.tracking.requestAuthorization()
                }
            }
        }
    ),
)
```

`AdInitializationPhase.BeforeMobileAdsInitialize` runs after UMP consent is determined and before native Google Mobile Ads SDK initialisation starts.

The hook's suspending body runs inside the library's internal scope. Hooks execute once per native initialisation attempt, ensuring that coroutine cancellation or re-initialisation does not duplicate or skip the prompt.

## Reading tracking authorisation state

```kotlin
when (adManager.tracking.status()) {
    AdTrackingAuthorization.Authorized -> Unit      // IDFA is available
    AdTrackingAuthorization.Denied -> Unit          // User declined tracking or disabled tracking globally
    AdTrackingAuthorization.NotDetermined -> Unit   // Prompt has not been displayed yet
    AdTrackingAuthorization.Restricted -> Unit      // Restricted by system policy (e.g. parental controls)
    AdTrackingAuthorization.NotApplicable -> Unit   // Android target (always)
}
```

`status()` is a synchronous call that reads the current platform status without presenting UI. `requestAuthorization()` is a suspending function that presents the system prompt (at most once per application installation).

On Android, `status()` always returns `AdTrackingAuthorization.NotApplicable`, allowing common Kotlin Multiplatform code to compile and execute safely across both platforms.

## Optional: Publisher first-party IDs

For publishers interested in maintaining custom identifier consistency for frequency capping or publisher reporting, Google AdMob supports optional Publisher Provided IDs (PPID).

PPID can be configured on supported ad requests via AdMob request configuration. Note that PPID is an optional AdMob feature and does not substitute for legal consent or ATT authorisation requirements.

For more details, see the official [Google Publisher Provided ID guidance](https://support.google.com/admob/answer/14199649).
