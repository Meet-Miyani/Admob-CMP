## Module map: one shared core, two thin platform adapters

_Encodes `admob-cmp/CLAUDE.md` invariants #1, #7._

dev.avinya.ads:admob-cmp is an umbrella artefact. It holds essentially no code of its own; it exists so that a consumer adds one dependency and gets both underlying modules, which it re-exports with Gradle api scope: admob-cmp-core and admob-cmp-compose.

admob-cmp-core has no Compose dependency. Its commonMain source set holds the public API — AdManager, the per-format controllers, AdPlacement, AdConfig, AdEvent, AdError, consent and diagnostics — plus the internal shared state machines FullScreenSlotCore, BannerCore, NativeAdCoordinatorCore, NativeAdSessionCore and AdRetry. The package dev.avinya.ads.appopen holds AppOpenAdCoordinator, while dev.avinya.ads.nativead holds the bounded native-session contract, policies, options and media information.

admob-cmp-compose holds everything that requires Compose Multiplatform: the dev.avinya.ads.ui composables BannerAdView and NativeAdView, the adLayout {} DSL with its validator and templates in dev.avinya.ads.nativead.layout, and the debug screen in dev.avinya.ads.debug.

androidMain supplies AndroidGoogleAdManager and Android native-session platform adapters backed by the GMA Next-Gen SDK on API level 26 and above, the AdMob.manager(context) singleton, and a ProcessLifecycleOwner foreground signal. iosMain supplies IosGoogleAdManager, iOS native-session adapters, banner and consent over Kotlin/Native cinterop bindings against GMA 13.x on iOS 15 and above, a UIKit native-ad renderer, and an NSNotificationCenter foreground signal.

Platform classes implement low-level operations only. The native coordinator owns platform ads, global reservations, exact retirement and session generations; platform adapters retain delegates and perform SDK calls on Main. No platform call occurs while coordinator or governor locks are held.

## Initialisation order: UMP consent, then ATT, then initialize

_Encodes `admob-cmp/CLAUDE.md` invariants #5, #11._

Initialising the library requires three sequential operations on iOS that must execute in strict order before loading ads.

Step one: call adManager.consent.gatherConsent(config). This executes Google's User Messaging Platform consent update and, under ConsentMode.GatherBeforeInitialize, displays the consent form when required by regional privacy regulations. UMP updates ConsentStatus and updates canRequestAds, which gates all subsequent ad requests. The SDK evaluates canRequestAds during load() and show(), and re-checks canPresent() at presentation time.

Step two: call adManager.tracking.requestAuthorization(). On iOS 14.5 and later, this presents the system App Tracking Transparency prompt and resolves to Authorized, Denied, Restricted or NotDetermined. The system prompt requires the NSUserTrackingUsageDescription key in the app target's Info.plist; without this key, iOS withholds access to the advertising identifier (IDFA). On Android, App Tracking Transparency is not applicable: adManager.tracking operates as a no-op and always returns AdTrackingAuthorization.NotApplicable.

Step three: call adManager.initialize(config, ConsentMode.InitializeOnlyIfAlreadyAllowed). The Google Mobile Ads SDK initialises and AdManagerStatus transitions to Ready, allowing ad requests to proceed.

The order is sequential because ad requests issued prior to App Tracking Transparency authorisation cannot retroactively attach an IDFA. Subsequent ad requests following user approval will attach the identifier subject to platform SDK rules. UMP consent gathering precedes the tracking prompt so the SDK can confirm whether ad requests are permitted for the current user session.

## Full-screen ad lifecycle: load, cache, show, reload

_Encodes `admob-cmp/CLAUDE.md` invariants #1, #2, #9._

FullScreenSlotCore provides the shared state machine for interstitial, rewarded, rewarded-interstitial and app-open ad formats. A controller begins in the Idle state. Calling load() transitions the state to Loading; success transitions to Loaded and places the ad into the cache; failure transitions to Failed after AdRetry exhausts backoff attempts for retryable errors. Calling show() presents the ad at the head of the cache.

The cache operates as a per-slot first-in-first-out queue bounded by AdCachePolicy.maxSize (defaulting to 1 entry). Expired entries are pruned upon access based on AdExpirationPolicy (one hour for standard full-screen formats, four hours for app-open ads).

The presentAd operation suspends until the ad is dismissed by the user. A presented ad is destroyed only upon normal completion, not upon coroutine cancellation, ensuring active screen presentation is preserved. Presentation ownership uses a single-use FullScreenPresentationHandle: shared core manages the handle until the platform layer invokes tryHandOffToCallbacks() immediately before calling the underlying SDK show method. From that point forward, only SDK terminal callbacks resolve presentation status.

Because presentation ownership hands off to the underlying platform SDK, show() is non-reentrant per controller instance. Calling show() while an ad is active on the same controller returns AdShowResult.NotReady immediately. Applications should await the outcome of a show() call before initiating another presentation.

Following dismissal, if AdCachePolicy.reloadAfterShow is true, the core automatically schedules an ad reload. Otherwise, the controller transitions to Loaded if remaining cached ads exist, or returns to Idle when empty.

Calling clear() increments an internal generation counter and clears cached ads. Every load attempt and scheduled reload evaluates its originating generation counter before publishing results, ensuring in-flight loads initiated prior to clear() are discarded rather than repopulating the cache.

All suspending operations enforce configured execution bounds. Ad loading operates within withTimeoutOrNull using placement.timeoutPolicy.loadTimeout, bounding the complete attempt sequence including backoff delays. Timeouts apply to the pre-hand-off window; once the underlying SDK assumes presentation control, presentation is not forcefully terminated.
<a id="native-session-lifecycle"></a>

## Native session lifecycle and bounded admission

_Encodes `admob-cmp/CLAUDE.md` invariants #3, #4, #8._

A named native session receives a bounded window of stable, model-owned slots from a measured viewport. It ranks visible slots before ahead and behind bands, and requests capacity from the process-wide governor before a platform load begins.

The default governor permits four speculative loaded-or-reserved ads and never permits more than six total. Visible demand can use hard-limit headroom; mounted records cannot be evicted. Session state publishes empty, loading, ready, mounted, retained and failed slots rather than exposing platform handles.

A successful load is a coordinator-owned retained record. NativeAdView may obtain one internal renderer lease for an exact slot generation. A row or tab detachment releases that renderer binding while the bounded record can remain available for reattachment.

TTL expiry, memory pressure, consent invalidation, clear and permanent close retire the record exactly once. Reservations are generation-bound, so a late callback or stale renderer release cannot modify a replacement record. Android synchronizes batch callback handoff; iOS retains strong delegate references alongside the record.

## Banner geometry: host-supplied width to resolved adaptive size

_Encodes `admob-cmp/CLAUDE.md` invariants #6._

Banner controllers operate independently of UI layout trees, receiving container width as a host-supplied parameter during ad loading.

In Compose UI applications, BannerAdView measures its parent layout bounds and supplies the resulting width as BannerGeometry(widthDp). Callers interacting directly with BannerController provide geometry explicitly, such as adManager.banner(placement).load(geometry = BannerGeometry(widthDp = 320)).

BannerCore resolves target width via geometry?.widthDp ?: platform.fallbackWidthDp(). The platform fallback returns null if window dimensions are unavailable, causing BannerCore to fail the load attempt with a clear error requiring explicit dimensions rather than applying arbitrary defaults.

On Android, the platform fallback derives width from the active Activity context when available. On iOS, fallback width is calculated from key window bounds to accommodate multitasking layouts such as Split View, Slide Over and popover windows.

Once width is established, BannerCore invokes platform.resolveSize(sizePolicy, widthDp) to derive platform-native ad dimensions, then executes loadBanner(size, sizePolicy, requestOptions, requiredGeneration).

Calling refresh() re-executes the complete resolved load request — including geometry, size policy and request options — from the previous load attempt. Calling registerGeometry() updates container measurements without triggering an immediate load, allowing manual refresh policies (BannerRefreshPolicy.Manual) to reload at updated container widths.
<a id="consent-decision-tree"></a>

## Consent decision tree: canRequestAds and the privacy-options button

_Encodes `admob-cmp/CLAUDE.md` invariants #5._

Consent management involves two distinct operational decisions: gating ad requests and displaying user privacy settings.

The first evaluation determines whether ad requests may proceed: adManager.consent.canRequestAds provides a `StateFlow<Boolean>` updated by the UMP SDK. When canRequestAds is false, load() and show() operations return AdErrorCode.CONSENT_REQUIRED, and canPresent() evaluates to false at presentation time. Configuring ConsentMode.GatherBeforeInitialize displays required consent forms during initialisation to establish this state.

The second evaluation determines whether the user interface should display a privacy settings button: apps check whether consent.privacyOptionsRequirementStatus equals PrivacyOptionsRequirementStatus.Required. When Required, the application presents a privacy options entry point linked to consent.showPrivacyOptions().

ConsentStatus.Obtained reflects UMP status but does not directly gate requests or UI buttons. For example, in regions outside the European Economic Area (EEA), UMP returns ConsentStatus.NotRequired while canRequestAds remains true, enabling ad serving without requiring consent form interaction.
<a id="retry-timeline"></a>

## Retry timeline: capped exponential backoff

_Encodes `admob-cmp/CLAUDE.md` invariants #9._

AdRetryPolicy configures automatic retry attempts using maxAttempts, where maxAttempts includes the initial load attempt. By default, maxAttempts is set to 2 (one initial attempt plus one retry). Setting maxAttempts to 1 disables retry attempts.

Backoff delay prior to retry n is calculated using min(initialDelay × backoffMultiplier^(n−1), maxDelay). Default settings (initialDelay of 2s, backoffMultiplier of 2.0, maxDelay of 30s) yield retry delays of 2s, 4s, 8s and 16s before capping at 30s.

Retry logic applies exclusively to transient network and system failures. On Android, retryable errors match GMA Next-Gen error codes NETWORK_ERROR, TIMEOUT and INTERNAL_ERROR. On iOS, retryable errors match numeric codes 2 (network), 5 (timeout) and 11 (internal).

Non-retryable conditions include no-fill responses (Android NO_FILL, iOS code 1) and configuration errors (INVALID_REQUEST, APP_ID_MISSING, INVALID_AD_RESPONSE). Operational gates such as consent_required or sdk_not_ready represent prerequisite checks rather than load failures and do not enter retry backoff.

The entire retry sequence executes within a top-level timeout managed by withTimeoutOrNull(placement.timeoutPolicy.loadTimeout) in the shared core. This outer timeout bounds total execution time across all retry attempts and backoff intervals.

## Platform support matrix: six formats on Android and iOS

_Encodes `admob-cmp/CLAUDE.md` invariants #11._

All six ad formats are supported on Android and iOS: banner (anchored adaptive, inline adaptive, fixed, fluid, and collapsible), interstitial, rewarded, rewarded interstitial, app-open, and native ads. Minimum platform versions are API level 26 for Android (GMA Next-Gen SDK) and iOS 15 for iOS (GMA 13.x SDK).

User Messaging Platform (UMP) consent flows, privacy settings forms, mediation adapter support, and revenue tracking via AdEvent.Paid operate across both platforms.

App Tracking Transparency (ATT) is an iOS-specific framework. On Android, adManager.tracking returns AdTrackingAuthorization.NotApplicable, and advertising identifier access relies on the AD_ID manifest permission. On iOS, ATT authorisation should be requested after UMP consent and prior to initialising the Google Mobile Ads SDK.

Native video lifecycle callbacks differ between platforms due to underlying SDK surfaces. iOS provides native video events (VideoStarted, VideoPlayed, VideoPaused, VideoEnded, and VideoMuted) via GADVideoControllerDelegate. Android GMA Next-Gen NativeAd does not expose corresponding video lifecycle callbacks, so cross-platform video handling should not rely on native video events on Android.

Request options immersiveMode, customClickGesture, publisherProvidedId, categoryExclusions, and skipUninitializedAdapters apply to Android and are ignored on iOS. Request parameters customTargeting and placementId map across both platforms.
